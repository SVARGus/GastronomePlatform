## 1. Context (Контекст)

Модульный монолит (ADR-0001) с 8 бизнес-модулями требует механизма асинхронного взаимодействия. Ряд бизнес-процессов не может быть реализован синхронно:

- **Заказ блюда** (Этап 6): создание заказа → резервирование доставки → уведомление исполнителю → подтверждение → оплата. Цепочка с внешними зависимостями, каждая из которых может быть временно недоступна.
- **Уведомления** (Этап 5): при публикации блюда, новом комментарии, изменении статуса заказа — подписчики получают email/push. Отправка не должна блокировать основную операцию.
- **Поиск** (будущее): при создании/обновлении блюда — индексация в Elasticsearch. Eventual consistency допустима.
- **Подписки** (Этап 3): при активации подписки — смена роли пользователя в модуле Users. При истечении — отзыв роли.

На текущем этапе (монолит) доменные события обрабатываются **in-process** через MediatR (ADR-0003). Но архитектура должна быть готова к переходу на межсервисную коммуникацию при выделении модулей. Нужен брокер сообщений, который:

- Прост в настройке и эксплуатации для одного разработчика.
- Поддерживает надёжную доставку (acknowledgements, dead-letter queues).
- Имеет хорошую интеграцию с .NET-экосистемой.
- Доступен как Docker-контейнер для локальной разработки.

## 2. Considered Alternatives (Рассмотренные альтернативы)

### Вариант A — Только MediatR (без внешнего брокера)

Все события обрабатываются in-process через `INotificationHandler<T>`. Нет внешнего брокера.

**Плюсы:** нулевая инфраструктурная сложность, мгновенная доставка, транзакционная гарантия (событие и обработчик в одном процессе).
**Минусы:** при падении приложения в момент обработки события — оно теряется безвозвратно. Нет персистентных очередей. При выделении модуля в микросервис — нужно с нуля внедрять брокер. Нет retry/dead-letter механизмов. Невозможно обработать событие отложенно (consumer отключён).

**Причина отклонения:** не обеспечивает отказоустойчивость для критичных процессов (заказы, платежи). При переходе к микросервисам — полная переработка коммуникации.

### Вариант B — Apache Kafka

Распределённый лог событий. Персистентный, горизонтально масштабируемый, гарантирует порядок внутри партиции.

**Плюсы:** высокая пропускная способность (миллионы msg/sec), персистентность (retention), replay событий, идеален для Event Sourcing и аналитики.
**Минусы:** высокая операционная сложность (ZooKeeper/KRaft, партиции, consumer groups). Для дипломного проекта с одним разработчиком — overkill. Требует значительных ресурсов (RAM, диск). Модель «лог» вместо «очередь» — менее интуитивна для простых сценариев pub/sub. Интеграция с .NET менее зрелая, чем RabbitMQ.

**Причина отклонения:** непропорциональная сложность для текущего масштаба. Kafka оправдан при миллионах событий в секунду и необходимости replay — ни то, ни другое не актуально для кулинарной платформы на старте.

### Вариант C — RabbitMQ ⭐

Брокер сообщений с моделью «очередь + exchange». Поддерживает AMQP, надёжную доставку (publisher confirms, consumer acknowledgements), dead-letter queues, management UI.

**Плюсы:** простота настройки и эксплуатации (один контейнер), management-панель для мониторинга очередей, зрелая интеграция с .NET (RabbitMQ.Client, MassTransit, EasyNetQ). Dead-letter exchange для обработки отравленных сообщений. Lightweight — минимальные требования к ресурсам. Достаточная пропускная способность для целевой нагрузки (сотни msg/sec).
**Минусы:** нет replay событий (сообщение удаляется после acknowledgement). Не подходит для Event Sourcing. При очень высокой нагрузке (>100K msg/sec) — масштабирование сложнее, чем Kafka.

**Сразу отвергнуто:** NATS (недостаточная персистентность в базовой конфигурации), Azure Service Bus / AWS SQS (vendor lock-in, требуют облачного аккаунта).

## 3. Decision (Принятое решение)

Использовать **RabbitMQ 3** как брокер сообщений для Event-Driven взаимодействия.

### Двухэтапная стратегия

**Этап 0–4 (текущий — монолит):**
- RabbitMQ развёрнут в docker-compose, доступен на порту 5672 (AMQP) и 15672 (management UI).
- Доменные события обрабатываются **in-process через MediatR** (`IDomainEvent : INotification`, `TaskWhenAllPublisher`).
- RabbitMQ **подготовлен, но не используется активно** — инфраструктура на месте для будущего перехода.
- Connection string прописан в `appsettings.Development.json`.

**Этап 5–8+ (переход к Integration Events):**
- При выделении модулей — Domain Events заменяются на Integration Events, публикуемые в RabbitMQ.
- Outbox Pattern (Этап 8) гарантирует атомарность «запись в БД + публикация события».
- Каждый микросервис подписывается на нужные события через собственную очередь.
- Dead-letter exchange для обработки отравленных сообщений.

### CorrelationId в событиях

При публикации в RabbitMQ — `CorrelationId` из HTTP-запроса пробрасывается в заголовках сообщения. Подписчик извлекает его и кладёт в `LogContext` — обеспечивается сквозная трассировка через Serilog + Seq.

### Конфигурация docker-compose

```yaml
rabbitmq:
  image: rabbitmq:3-management
  container_name: gastronome-rabbitmq
  restart: unless-stopped
  ports:
    - "5672:5672"       # AMQP
    - "15672:15672"     # Management UI
  environment:
    RABBITMQ_DEFAULT_USER: gastronome
    RABBITMQ_DEFAULT_PASS: gastronome123
  volumes:
    - rabbitmq-data:/var/lib/rabbitmq
  healthcheck:
    test: ["CMD", "rabbitmq-diagnostics", "-q", "ping"]
    interval: 10s
    timeout: 5s
    retries: 5
    start_period: 20s
```

## 4. Rationale (Обоснование)

1. **Простота для одного разработчика.** RabbitMQ — один контейнер, management UI для мониторинга, минимальная конфигурация. Kafka требует ZooKeeper/KRaft, партиционирование, consumer groups — всё это операционная нагрузка без пользы на текущем масштабе.

2. **Зрелая .NET-экосистема.** `RabbitMQ.Client` — официальный клиент. MassTransit — полноценный фреймворк с Outbox, Saga, retry из коробки. При необходимости — подключается одной строкой в DI.

3. **Надёжная доставка.** Publisher confirms + consumer acknowledgements + dead-letter exchange — стандартные механизмы RabbitMQ, покрывающие сценарии «событие не потеряется» и «отравленное сообщение не заблокирует очередь».

4. **Подготовка к микросервисам без преждевременной сложности.** RabbitMQ развёрнут и готов, но на Этапах 0–4 не создаёт операционной нагрузки (события идут через MediatR). Переход на RabbitMQ — замена `INotificationHandler<T>` на RabbitMQ consumer без изменения бизнес-логики.

5. **Соответствие профилю нагрузки.** Кулинарная платформа — сотни, не миллионы событий в секунду. RabbitMQ легко справляется с этой нагрузкой на одном узле. Кластеризация (Этап 8+) добавляет HA при необходимости.

## 5. Consequences (Последствия)

### Positive (Положительные)
- Инфраструктура брокера на месте с Этапа 0 — переход от in-process к межсервисным событиям не потребует смены инфраструктуры.
- Management UI (`localhost:15672`) — мониторинг очередей, потребителей, скорости обработки без дополнительных инструментов.
- Dead-letter exchange — отравленные сообщения не блокируют обработку, можно анализировать отдельно.
- Healthcheck в docker-compose — `docker compose ps` показывает реальный статус (`healthy`).

### Negative / Trade-offs (Отрицательные / компромиссы)
- На Этапах 0–4 RabbitMQ потребляет ресурсы (RAM ~150–200 MB), но не используется активно. Приемлемо для разработки.
- Нет replay событий — если подписчик пропустил событие и оно было acknowledged, восстановить невозможно. Митигация: Outbox Pattern (Этап 8).
- Дополнительная точка отказа — если RabbitMQ упадёт при переходе к Integration Events, события не будут доставлены. Митигация: кластеризация (Этап 8+), Outbox как буфер.
- Операционно: пароли в открытом виде в docker-compose (только для разработки).

### Areas of Caution (На что обратить внимание)
- При переходе к Integration Events — не забыть пробрасывать `CorrelationId` в заголовках сообщения.
- Outbox Pattern обязателен для критичных событий (заказы, платежи) — без него возможна потеря событий при падении между коммитом БД и публикацией в RabbitMQ.
- Идемпотентность обработчиков — RabbitMQ может доставить сообщение повторно (at-least-once). Все обработчики должны быть идемпотентными.
- При мониторинге в продакшене — следить за глубиной очередей (alert при росте).

## 6. Future Scope (Будущие направления)

- **Этап 5+:** Первые Integration Events через RabbitMQ. Кандидаты — события подписок (`SubscriptionActivatedEvent` и родственные): на Этапе 3 они уже обрабатываются in-process listener-ами (назначение роли Premium), при выделении модулей переезжают в брокер без изменения подписчиков.
- **Этап 6:** Оркестрация заказов через события — `OrderCreated` → `DeliveryScheduled` → `PaymentProcessed`.
- **Этап 8:** Outbox Pattern — транзакционная публикация событий. MassTransit Outbox или Wolverine.
- **Этап 8+:** Кластеризация RabbitMQ (master + replicas) для HA. Quorum queues для критичных очередей.
- **При высокой нагрузке:** рассмотреть переход на Kafka для event-heavy модулей (Analytics, Search) при сохранении RabbitMQ для задач с гарантированной доставкой (Orders, Payments).
