## 1. Context (Контекст)

Блюдо на платформе живёт долго: автор публикует, вносит правки, снова публикует. Между публикациями посетители читают опубликованную версию. Возникает вопрос: **сколько исторических версий опубликованных данных нужно хранить**?

Сценарии, потенциально требующие истории версий:
- **Откат к предыдущей версии.** Автор ошибочно опубликовал сырую правку — хочет вернуться к предыдущей стабильной.
- **Аудит правок.** Модератор или админ смотрит, что именно менялось в спорном блюде.
- **Сравнение версий.** UI-функция «показать что изменилось со времени вашего последнего просмотра» для подписчиков автора.
- **Юридическая фиксация.** Кто-то заказал блюдо по конкретной версии рецепта — эту версию нужно сохранить как есть.
- **Обучение AI-модели.** История правок как обучающая выборка (Этап 8+ или позже).

Хранение всех версий имеет стоимость: место в БД (jsonb-снепшот × N версий × M блюд), сложность запросов, дополнительные миграции, риск ошибок при работе с версиями.

Проектирование Этапа 2 требовало определить: **вводить ли историю версий сразу или отложить**?

## 2. Considered Alternatives (Рассмотренные альтернативы)

### Вариант A — Полная история публикаций сразу (таблица `DishVersion`)

Каждый `PublishDish` создаёт новую запись в `DishVersion` со снепшотом. `Dish.PublishedVersionData` не хранит текущее состояние — оно вычисляется как `TOP 1 FROM DishVersion WHERE DishId = @id ORDER BY VersionNumber DESC`.

**Плюсы:**
- Полная история сразу — все сценарии выше доступны без миграций.
- Юридическая фиксация «работает из коробки».
- Простая семантика: «снепшот = запись в истории».

**Минусы:**
- Каждая карточка блюда для посетителя = JOIN с `DishVersion` + подзапрос «последняя версия». Простой `SELECT * FROM Dish WHERE id = @id` перестаёт работать.
- Хранилище растёт линейно с количеством публикаций. При 100K блюд × 10 средних правок = 1M снепшотов × 5–30 KB = 5–30 GB только под историю.
- Каскадные обновления при переименовании категории (Этап 8+) должны трогать все версии или помечать «применимо от версии N» — сложнее.
- 90% этой функциональности не будет использовано никогда (большинство блюд публикуются 1–3 раза за жизнь).

### Вариант B — Только текущая опубликованная версия (`PublishedVersionData`) ⭐

`Dish.PublishedVersionData` (jsonb) хранит **только** текущий опубликованный снепшот. При новой публикации — перезаписывается. История не хранится.

**Плюсы:**
- Простая модель хранения: одна строка в `Dish` — одна карточка для посетителя.
- Минимальное дублирование: 100K блюд × 1 снепшот = 500 MB – 3 GB (приемлемо).
- Каскадные обновления Этапа 8+ работают с одной строкой на блюдо.
- Отдача карточки посетителю — один `SELECT` без JOIN (см. ADR-0011).

**Минусы:**
- Нет истории — сценарии «откат», «аудит», «сравнение» не поддерживаются.
- Юридическая фиксация «блюдо на момент заказа» требует отдельного решения (снепшот в `OrderItem`, Этап 6+).

**Причина выбора:** соответствует профилю нагрузки Этапа 2 (только просмотр и правка автором), минимизирует хранилище и сложность, откладывает историю до появления реальных сценариев её использования.

### Вариант C — Гибрид: текущая версия + N последних (`DishVersion` с обрезкой)

`Dish.PublishedVersionData` — текущая версия. `DishVersion` — последние N (например, 5) исторических.

**Плюсы:** ограниченный размер истории, поддержка «отката на 1–2 версии назад».
**Минусы:**
- Всё усложнение Варианта A, но с ограниченной пользой (отката на 10-ю версию нет).
- Нужен механизм обрезки: старые версии удаляются при превышении N. Это порождает вопросы: «а как быть с версией, на которую сослался Order?».
- Компромисс, который не решает ни задачу «полная история», ни задачу «минимальное хранилище».

**Причина отклонения:** промежуточное решение, которое не даёт полной ценности ни одного из подходов и добавляет сложности механизма обрезки.

## 3. Decision (Принятое решение)

**На Этапе 2 хранится только текущая опубликованная версия блюда — в поле `Dish.PublishedVersionData` (jsonb).** Историческая таблица `DishVersion` не создаётся.

### Правила хранения

- `Dish.PublishedVersionData jsonb NULL` — единственное место хранения опубликованной версии.
- `NULL` — блюдо не опубликовано (статус `Draft`) либо снято с публикации (`Unpublished`/`Archived`).
- Не `NULL` — блюдо опубликовано; снепшот отражает состояние на момент последнего `PublishDish` (либо каскадной пересборки, Этап 8+).

### Правила поведения UC

- **UC-DSH-004 PublishDish** → перезаписывает `PublishedVersionData`. Предыдущая версия **теряется** — история не сохраняется.
- **UC-DSH-005 Unpublish** → `PublishedVersionData = NULL`. Автор может продолжить правки и опубликовать снова.
- **UC-DSH-006 Archive** → `PublishedVersionData = NULL`. Блюдо становится неактивным.
- **UC-DSH-054 SearchDishes** и **UC-DSH-050..052** (просмотр карточки) → читают из `PublishedVersionData` напрямую.

### Отсутствующие функции (осознанно не реализуются на Этапе 2)

- Откат к предыдущей версии.
- Просмотр истории публикаций.
- Сравнение версий (diff).
- Уведомление подписчиков «блюдо изменилось» с указанием diff.

Юридическая фиксация «блюда на момент заказа» решается **не на стороне Dishes**, а в модуле Orders (Этап 6+): `OrderItem.DishSnapshot jsonb` — копия релевантной части снепшота в момент оформления заказа. Orders не зависят от состояния Dish после оформления.

## 4. Rationale (Обоснование)

1. **Профиль нагрузки Этапа 2 не требует истории.** Основные сценарии — просмотр каталога, чтение карточек, правка автором. Все они работают с «текущим состоянием», не с историей.

2. **Экономия хранилища и сложности.** Хранение 1 версии вместо N — линейная экономия места в БД и упрощение всех запросов, каскадных обновлений, кэширования.

3. **Юридическая фиксация — отдельная задача другого модуля.** Заказы фиксируют состояние блюда в своём снепшоте (`OrderItem.DishSnapshot`), это часть модели данных Orders (Этап 6+). Смешивать «историю правок автора» и «состояние на момент заказа» — некорректно семантически.

4. **YAGNI.** Реальные сценарии использования истории версий на текущем этапе неизвестны. Проектирование под гипотетические сценарии «сравнение версий», «откат» — преждевременная оптимизация. Deferred до появления реального запроса.

5. **Обратимость решения дешёвая.** Добавление таблицы `DishVersion` на Этапе 4+/8+ — миграция без изменения текущей модели. `PublishedVersionData` остаётся источником текущей карточки; `DishVersion` появляется как append-only лог, заполняемый при `PublishDish` от этапа введения.

## 5. Consequences (Последствия)

### Positive (Положительные)
- Минимальная модель хранения — одна строка на блюдо в `Dish`.
- Все запросы каталога и карточки работают с одним jsonb-полем.
- Каскадные обновления (Этап 8+) трогают одну версию на блюдо.
- Простая семантика для разработчика: «есть `PublishedVersionData` — блюдо опубликовано, нет — не опубликовано».

### Negative / Trade-offs (Отрицательные / компромиссы)
- Откат к предыдущей версии на Этапе 2 невозможен. Митигация: UC-DSH-005 «Unpublish» временно снимает блюдо с публикации, автор правит рабочую версию, публикует заново. Не откат в буквальном смысле, но покрывает основной сценарий «сломал публикацию, хочу починить».
- История правок для юридических целей отсутствует. Митигация: `OrderItem.DishSnapshot` в Orders (Этап 6+), не в Dishes.
- Диффов между версиями нет. Соответствующие UI-функции («что изменилось со времени вашей последней проверки») не реализуются. Митигация: приходит с введением `DishVersion` (Этап 4+/8+).

### Areas of Caution (На что обратить внимание)
- Если в будущем понадобится откат — вводить `DishVersion` через отдельную миграцию, не менять `PublishedVersionData`.
- Модуль Orders (Этап 6+) обязан сохранять снимок блюда сам, не полагаясь на «версию Dish на момент заказа». Иначе изменение блюда автором позже сломает историю заказов.
- Не путать «Unpublish» (обнуление `PublishedVersionData`) с «Archive» (полное снятие блюда). Обе операции обнуляют снепшот, но семантически разные (см. UC-DSH-005 и UC-DSH-006).

## 6. Future Scope (Будущие направления)

- **Этап 4+ или 8+:** Введение `DishVersion` — append-only таблица со снепшотами каждой публикации. Триггер введения — реальный запрос от бизнеса или пользователей (аудит модерации, откат, сравнение). До этого — не реализуется.

  Предварительная структура при введении:

  | Поле | Тип |
  |------|-----|
  | Id | uuid |
  | DishId | uuid FK |
  | VersionNumber | int |
  | VersionData | jsonb |
  | ActionType | enum (Published, Updated, Deleted) |
  | ActionAt | timestamptz |
  | ActionByUserId | uuid |
  | ActionReason | varchar(500) NULL |

- **Этап 6+:** Модуль Orders реализует `OrderItem.DishSnapshot jsonb` — независимая юридическая фиксация состояния блюда на момент оформления заказа. Не зависит от `DishVersion`, работает даже если Dishes на Этапе 2.

- **Этап 8+:** При появлении `DishVersion` — стратегии управления размером (партиционирование по году, хранение последних N версий, перенос старых в холодное хранилище).

## 7. Implementation Reference (Связь с кодовой базой)

- `src/Modules/Dishes/.../Domain/Entities/Dish.cs` — поле `PublishedVersionData` (string?), метод `Publish(DateTimeOffset utcNow, string snapshot)` перезаписывает поле, методы `Unpublish(utcNow)` и `Archive(utcNow)` обнуляют.
- `src/Modules/Dishes/.../Application/Commands/PublishDish/PublishDishCommandHandler.cs` — сборка снепшота из полного агрегата, передача в `Dish.Publish(...)`.
- **Отсутствует:** `DishVersion.cs`, `IDishVersionRepository.cs` — не создаются на Этапе 2 согласно данному ADR.
- **Будущее (Этап 6+):** `OrderItem.DishSnapshot` в модуле Orders — независимая копия состояния блюда для юридической фиксации заказа.
