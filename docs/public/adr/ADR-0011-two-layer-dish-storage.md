## 1. Context (Контекст)

Модуль Dishes — ядро кулинарной платформы. Агрегат `Dish` содержит рецепт, шаги приготовления, ингредиенты, теги, категории, тайминги, выход порций. Полная «карточка» блюда для отдачи посетителю требует данных из 7+ связанных таблиц.

Профиль нагрузки платформы — **read-heavy**: подавляющее большинство пользователей просматривают каталог и карточки блюд; авторы редко правят свои рецепты. При этом:

- Каталог требует быстрой фильтрации и сортировки по реляционным полям (категория, рейтинг, тег, сложность).
- Карточка блюда для посетителя требует отдачи всех данных одним запросом — 5+ JOIN-ов при каждом просмотре неприемлемы.
- Авторская правка не должна немедленно менять то, что видят посетители — нужна явная операция «Опубликовать».

Необходимо найти баланс между производительностью чтения, целостностью данных и семантикой публикации.

## 2. Considered Alternatives (Рассмотренные альтернативы)

### Вариант A — Чисто реляционная модель (без снепшота)

Все данные в нормализованных таблицах. Карточка блюда собирается через JOIN при каждом запросе.

**Плюсы:** единый источник правды, нет дублирования данных, привычный EF Core `Include()`.
**Минусы:** карточка блюда = 5+ JOIN-ов (`Dish` → `Recipe` → `RecipeStep` × N → `RecipeIngredient` × M → `Ingredient` → `DishCategory` → `Category` → `DishTag` → `Tag` + `Timing` + `Yield`). На каждый просмотр — десятки строк. При 100+ RPS на каталог — нагрузка на БД растёт линейно. Нет механизма «автор правит черновик, посетитель видит опубликованную версию» без дополнительной логики.

**Причина отклонения:** неприемлемая производительность чтения для read-heavy платформы. Отсутствие семантики публикации.

### Вариант B — Всё в jsonb (без реляционных таблиц)

Данные блюда хранятся целиком в jsonb-поле. Фильтрация через GIN-индексы.

**Плюсы:** один столбец — один запрос. Схема гибкая, не нужны миграции при добавлении полей.
**Минусы:** GIN-индексы на jsonb медленнее B-tree в 3–5 раз для типичных фильтров каталога. Сортировка по jsonb-полям не использует обычные B-tree индексы. Каскадные обновления по справочникам (переименование категории → пересборка всех блюд с этой категорией) требуют full scan по jsonb. EF Core с jsonb-операторами дружит хуже, чем с реляционными связями.

**Причина отклонения:** производительность фильтрации каталога критически страдает. Потеря реляционных связей для M:M (теги, категории).

### Вариант C — Гибрид: реляционные таблицы + jsonb-снепшот ⭐

Реляционные таблицы — источник правды для запросов, фильтрации, авторской правки. Jsonb-поле `PublishedVersionData` — готовая денормализованная карточка для отдачи посетителю. Отдельные `*Published`-таблицы для каталожного фильтра по опубликованным M:M-связям.

**Плюсы:** фильтрация каталога по B-tree индексам (реляционные колонки), отдача карточки за один запрос без JOIN (jsonb), явная семантика публикации (снепшот пересобирается только при `Publish`), авторские правки не влияют на посетителей до публикации.
**Минусы:** дублирование данных между реляционными таблицами и снепшотом. Снепшот может устареть при каскадных админских операциях (переименование категории) — требуется механизм инвалидации (Этап 8+).

## 3. Decision (Принятое решение)

В агрегате `Dish` используется **двухслойная модель данных** с осознанным дублированием.

### 3.1. Три источника данных

| Источник | Назначение | Обновляется |
|----------|-----------|-------------|
| **Основные таблицы** (`Dish`, `Recipe`, `RecipeStep`, `RecipeIngredient`, `DishCategory`, `DishTag` и пр.) | Источник правды: фильтрация, сортировка, авторская правка | При каждой правке автора |
| **`Dish.PublishedVersionData` (jsonb)** | Готовая карточка для отдачи посетителю | Только при `UC-DSH-004 PublishDish` (+ каскадная пересборка Этап 8+) |
| **`*Published`-таблицы** (`DishCategoryPublished`, `DishTagPublished`) | Каталожный фильтр по тегам/категориям **опубликованной** версии | Синхронно при `PublishDish` и админских операциях над справочниками (Этап 8+) |

### 3.2. Семантика обновления и чтения

- **Авторская правка** (UC-DSH-002, 003, 007, 008, 020–033, 040–042) → только основные таблицы. Снепшот и `*Published`-таблицы не трогаются. Посетители видят старую опубликованную версию.
- **`UC-DSH-004 PublishDish`** → атомарно в одной транзакции: пересборка `PublishedVersionData`, перезапись `*Published`-таблиц из текущих `DishCategory`/`DishTag`, обновление `PublishedAt = now` (при **каждой** публикации, не только первой) и `PublishedVersionUpdatedAt = now`.
- **`UC-DSH-005 Unpublish`** → `PublishedVersionData = NULL`, записи в `*Published`-таблицах удаляются, `PublishedAt = NULL`, `PublishedVersionUpdatedAt = NULL`. Основные таблицы не трогаются — автор может продолжить правки.
- **`UC-DSH-006 Archive`** → аналогично Unpublish в части снепшота и `*Published`. Статус меняется на `Archived`.
- **Чтение.** Публичные запросы (UC-DSH-050/051/052) отдают снепшот. Автор/admin может явно запросить **рабочую версию** параметром `?version=working` (частичная реализация UC-DSH-083) — источник данных веб-редакторов: правки видны в редакторе сразу, на витрине — только после перепубликации.
- **Каскадные операции** (переименование категории, объединение тегов — Этап 8+) → реляционные связи и `*Published`-таблицы обновляются синхронно в транзакции админской операции; jsonb-снепшот пересобирается асинхронно через журнал `DishSnapshotInvalidation`. Подробнее — раздел 3.5.

### 3.3. Четыре временные метки

| Поле | Что отражает | Когда обновляется |
|------|-------------|-------------------|
| `CreatedAt` | Создание блюда | Один раз, иммутабельно |
| `UpdatedAt` | Последняя правка автора над содержимым блюда | При изменении данных автором (Interceptor + `MarkAsUpdated()`, см. §3.4) |
| `PublishedAt` | Последняя публикация автором | При каждом `PublishDish`; обнуляется при `Unpublish`/`Archive` |
| `PublishedVersionUpdatedAt` | Последнее обновление снепшота | При `PublishDish` + при каскадной пересборке (Этап 8+); обнуляется при `Unpublish`/`Archive` |

**Индикатор «есть неопубликованные правки»:** `UpdatedAt > PublishedAt`. Работает во всех сценариях, включая `PublishedAt = NULL` («блюдо не опубликовано»). Индикатор используется UI: плашка на витрине для автора, бейдж и кнопка «Опубликовать правки» в «Моих блюдах».

### 3.4. Два механизма обновления `UpdatedAt`

Автоматическое обновление `UpdatedAt` работает через `SaveChangesInterceptor` в EF Core, но не покрывает все сценарии. Полная модель — комбинация двух механизмов. Полный разбор реализации Interceptor — в отдельном [ADR-0019](./ADR-0019-dish-updated-at-interceptor.md); здесь фиксируется только доля Interceptor'а в семантике двухслойной модели.

**Механизм 1 — `SaveChangesInterceptor` (автоматический, defensive-слой).**

Interceptor настроен на 7 сущностей агрегата: `Dish`, `Recipe`, `RecipeStep`, `RecipeIngredient`, `Timing`, `Yield`, `Nutrition`. Для `Dish` изменения полей `PublishedVersionData`, `PublishedVersionUpdatedAt`, `RatingAvg`, `RatingCount`, `ViewsCount`, `FavoritesCount`, `UpdatedAt` НЕ триггерят `UpdatedAt` — это не «правки автора» (последнее исключение — чтобы поле не триггерило само себя).

**Приоритет домена.** Если Domain уже проставил `UpdatedAt` в этой же операции (wrapper-метод вызвал `MarkAsUpdated`, либо lifecycle-метод `Publish/Unpublish/Archive` присвоил напрямую) — Interceptor **не перетирает** значение (проверка `Property(UpdatedAt).IsModified`). Это принципиально для инварианта `UpdatedAt > PublishedAt`: `Publish` присваивает обеим меткам один и тот же `utcNow`, и перезапись `UpdatedAt` временем интерсептора (на доли миллисекунды позже) ложно поднимала бы индикатор «есть правки» сразу после каждой публикации.

**Механизм 2 — явный вызов `Dish.MarkAsUpdated(utcNow)`.**

Требуется в случаях, когда Interceptor не срабатывает:
- Изменения связующих таблиц M:M (`DishCategory`, `DishTag`) — Interceptor их не отслеживает. Wrapper-методы `Dish.SetCategories(...)` и `Dish.SetTags(...)` вызывают `MarkAsUpdated` вручную.
- Wrapper-методы агрегата над рецептом (`UpdateRecipe`, `AddRecipeStep`, `ReorderRecipeIngredients` и пр.) вызывают `MarkAsUpdated` явно — Interceptor остаётся защитой для случаев модификации дочерней сущности мимо wrapper'а.

### 3.5. Каскадные обновления снепшота (Этап 8+)

Каскадное обновление возникает, когда админская операция над справочником (переименование `Category.Name`, объединение двух `Tag`-ов) должна отразиться в снепшотах всех блюд, использующих эту сущность.

**Разделение синхронного и асинхронного:**

- **Синхронно** (в транзакции админской операции): изменение справочника; обновление реляционных связей (FK); обновление `*Published`-таблиц — для мгновенно-актуального фильтра каталога; запись в журнал `DishSnapshotInvalidation` со списком затронутых блюд.
- **Асинхронно** (фоновая задача `RecalculatePublishedSnapshots`): обход журнала; пересборка `PublishedVersionData` из основных таблиц; обновление `PublishedVersionUpdatedAt = now`. `UpdatedAt` НЕ обновляется — это системная операция, не правка автора.

**Обоснование разделения:** синхронная пересборка jsonb-снепшотов для 10000 блюд при переименовании популярной категории заблокирует БД на минуты. Асинхронная позволяет админу мгновенно завершить операцию; каталожный фильтр корректен немедленно, потому что `*Published`-таблицы обновлены синхронно.

### 3.6. Правило проектирования полей

- Поле с фильтром/сортировкой/JOIN → обязательно в основной таблице.
- Поле только для отдачи → может жить только в снепшоте.
- Поле для обоих целей → дублируется.
- Динамические счётчики (`RatingAvg`, `RatingCount`, `ViewsCount`, `FavoritesCount`) → только в основных колонках. Не включаются в снепшот, потому что обновляются между публикациями (при новом отзыве, при просмотре).

## 4. Rationale (Обоснование)

1. **Профиль нагрузки.** Кулинарная платформа — 95% чтений, 5% записей. Снепшот оптимизирует самый частый сценарий (просмотр карточки) за счёт усложнения самого редкого (публикация).

2. **Один запрос на карточку.** Посетитель получает полную карточку (рецепт + шаги + ингредиенты + теги + категории + Timing + Yield) одним `SELECT ... WHERE id = @id` без JOIN. HTTP-заголовок `Last-Modified` может браться из `PublishedVersionUpdatedAt` (Этап 4+, HTTP-кэш).

3. **Фильтрация каталога по B-tree.** `WHERE d.diet_labels_mask & 1 = 1 AND dcp.category_id = @id AND d.rating_avg >= 4.0 ORDER BY d.views_count DESC` — все поля в обычных колонках с обычными индексами. Никаких GIN-операторов.

4. **Семантика публикации.** Автор правит черновик → посетитель не видит незавершённых правок → автор нажимает «Опубликовать» → снепшот пересобирается атомарно. Естественная UX-модель для контентной платформы.

5. **Подготовка к каскадным обновлениям.** `*Published`-таблицы обновляются синхронно при админских операциях — каталожный фильтр сразу актуален. Jsonb-снепшот (визуальная карточка) пересобирается асинхронно — допустимая задержка (секунды–минуты).

6. **Разделение семантик четырёх меток.** `UpdatedAt` отвечает за «есть ли что публиковать» (UI-индикатор). `PublishedAt` фиксирует момент последней публикации (аудит). `PublishedVersionUpdatedAt` — для HTTP-кэшей и синхронизации со снепшотом. Одно поле для всего создало бы неоднозначности.

## 5. Consequences (Последствия)

### Positive (Положительные)

- Просмотр карточки — один запрос к БД, без JOIN, предсказуемая латентность.
- Каталог — фильтрация и сортировка по B-tree индексам, производительность не зависит от количества полей в снепшоте.
- Авторские правки изолированы от публичной версии — невозможно случайно «сломать» карточку незавершённой правкой; редакторы при этом видят рабочую версию через `?version=working`.
- `*Published`-таблицы позволяют фильтровать каталог по тегам/категориям **опубликованной** версии, а не рабочей.
- Индикатор «есть неопубликованные правки» (`UpdatedAt > PublishedAt`) — простой SQL-предикат, не требует отдельного вычисляемого поля.

### Negative / Trade-offs (Отрицательные / компромиссы)

- Дублирование данных — при публикации нужно собрать снепшот из 7+ таблиц и записать как JSON. Дополнительная логика в Application-слое (`IPublishedDishSnapshotBuilder`).
- Снепшот может устареть при каскадных админских операциях — требуется механизм инвалидации (`DishSnapshotInvalidation`, Этап 8+). До этого этапа каскадные операции просто не реализуются.
- `PublishedVersionData` увеличивает размер строки `Dish` на 5–30 KB (типичный опубликованный рецепт: карточка + 5–10 шагов + 10–15 ингредиентов). При 100K блюд — 500 MB – 3 GB дополнительно. Приемлемо для PostgreSQL.
- Четыре временные метки вместо одного `UpdatedAt` — сложнее для понимания, но каждая имеет чёткую семантику.
- Два механизма обновления `UpdatedAt` (Interceptor + `MarkAsUpdated`) — усложнение, требующее внимания при добавлении новых wrapper-методов (см. ADR-0019).

### Areas of Caution (На что обратить внимание)

- При добавлении новых полей в `Dish` — явно определить, должны ли они триггерить `UpdatedAt` (правка автора) или нет (счётчики, снепшот). Полный список исключаемых полей и обоснование каждого — в [ADR-0019](./ADR-0019-dish-updated-at-interceptor.md).
- Изменения `DishCategory`/`DishTag` требуют явного `MarkAsUpdated()` — Interceptor их не отслеживает.
- **Lifecycle-методы и незагруженные коллекции.** `Publish/Unpublish/Archive` вызывают `Clear()` на `*Published`-коллекциях. Lazy loading в проекте выключен: если агрегат загружен без `Include` этих коллекций, `Clear()` — no-op, старые строки выживают в БД, и повторная публикация падает дубликатом composite PK (23505). Хендлеры lifecycle-команд обязаны использовать репозиторные методы с `Include` обеих `*Published`-коллекций (`GetByIdWithFullRecipeAsync`, `GetByIdWithPublishedLinksAsync`).
- Снепшот передаётся в `Dish.Publish()` готовой строкой JSON из Application — Domain не знает о сериализации. `IPublishedDishSnapshotBuilder` — интерфейс уровня Application.
- **Jsonb-канонизация PostgreSQL** пересортировывает ключи объекта — полиморфная десериализация снепшота не может полагаться на позицию дискриминатора `type`. Решение (кастомный конвертер в `SnapshotJsonOptions`) — в ADR-0012, Areas of Caution.
- Динамические счётчики (`RatingAvg`, `ViewsCount`, ...) НЕ включаются в снепшот — всегда читаются из основных колонок.
- При падении фоновой задачи `RecalculatePublishedSnapshots` (Этап 8+) снепшоты могут разъехаться с реляционными данными на минуты-часы. Митигация: мониторинг задачи, ретраи, health-check.

## 6. Future Scope (Будущие направления)

- **Этап 5+:** остаток UC-DSH-083 — откат рабочей версии к снепшоту («удалить черновик»), представление правок отдельной строкой-черновиком в списках автора.
- **Этап 8+:** `DishSnapshotInvalidation` — журнал для асинхронной пересборки снепшотов при каскадных админских операциях + фоновая задача `RecalculatePublishedSnapshots` (раздел 3.5).
- **Этап 8+:** Трёхслойная модель — `Dish.DraftVersionData jsonb` при появлении конкурентных правок несколькими ролями (автор + ассистент + модератор).
- **Этап 4+/8+:** `DishVersion` — полная история публикаций (см. ADR-0009). При введении каждая запись будет содержать снепшот в формате текущего `PublishedVersionData`.

## 7. Implementation Reference (Связь с кодовой базой)

**Domain** (`src/Modules/Dishes/GastronomePlatform.Modules.Dishes.Domain/`):

- `Entities/Dish.cs` — поля `PublishedVersionData` (string?, jsonb), `PublishedVersionUpdatedAt`, `PublishedAt` (`DateTimeOffset?`), `CreatedAt`/`UpdatedAt` (`DateTimeOffset`); счётчики `RatingAvg`, `RatingCount`, `ViewsCount`, `FavoritesCount`. Lifecycle-методы:
  - `Publish(DateTimeOffset utcNow, string snapshot)` → `Result` — повторяет инварианты `CheckCanPublish()` (defense-in-depth, ADR-0015), затем `PublishedVersionData = snapshot`, `PublishedAt = PublishedVersionUpdatedAt = UpdatedAt = utcNow`, полная перезапись `_categoriesPublished`/`_tagsPublished` из рабочих коллекций, событие `DishPublishedEvent`.
  - `Unpublish(DateTimeOffset utcNow)` / `Archive(DateTimeOffset utcNow)` — обнуляют снепшот и метки публикации, очищают `*Published`-коллекции, поднимают `DishUnpublishedEvent`/`DishArchivedEvent`, `UpdatedAt = utcNow`.
- `Entities/DishCategoryPublished.cs`, `Entities/DishTagPublished.cs` — композитные ключи `(DishId, CategoryId)`/`(DishId, TagId)`.

**Application** (`src/Modules/Dishes/GastronomePlatform.Modules.Dishes.Application/`):

- `Commands/PublishDish/PublishDishCommandHandler.cs` — pre-check `CheckCanPublish()` → сборка снепшота → `dish.Publish(...)`.

- `Snapshots/IPublishedDishSnapshotReader.cs` + `PublishedDishSnapshotReader.cs` — обратный парсинг для UC-DSH-050/051/052.
- `Snapshots/SnapshotJsonOptions.cs` — единые настройки сериализации, включая конвертер полиморфных позиций (jsonb-канонизация, ADR-0012).
- `Queries/GetDishById`, `GetDishBySlug`, `GetDishRecipe` — чтение снепшота; `GetDishById`/`GetDishRecipe` поддерживают `?version=working` для автора/admin.

**Infrastructure** (`src/Modules/Dishes/GastronomePlatform.Modules.Dishes.Infrastructure/`):

- `Persistence/Configurations/DishConfiguration.cs` — `PublishedVersionData` как `jsonb`; все метки — `timestamp with time zone`.

На рабочих `DishCategoryConfiguration`/`DishTagConfiguration` таких индексов нет — рабочие таблицы не участвуют в каталожных запросах.
