## 1. Context (Контекст)

GastronomePlatform — дипломный проект, объединяющий каталог рецептов, систему подписок, маркетплейс заказов и социальные функции. Система включает минимум 8 бизнес-доменов с различными паттернами нагрузки (каталог — read-heavy, заказы — write-heavy, уведомления — асинхронные).

Ограничения проекта:

- Один разработчик (junior-уровень) — операционная сложность должна быть минимальной.
- Сроки ограничены учебным процессом (ВКР).
- Бюджет минимальный — Docker для локальной разработки, без managed-сервисов на старте.
- При этом система должна демонстрировать зрелые архитектурные подходы и допускать эволюцию при росте команды и нагрузки.

Требовалось выбрать архитектурный стиль, который позволит одному разработчику реализовать систему в разумные сроки, но при этом заложит фундамент для масштабирования.

---

## 2. Considered Alternatives (Рассмотренные альтернативы)

### Вариант A — Классический монолит

Единое приложение без внутреннего разделения на модули: все домены в одном проекте, общие модели данных, прямые вызовы между компонентами.

**Плюсы:** максимальная простота на старте, быстрая разработка первых функций, единый деплой.
**Минусы:** при росте функциональности (8 доменов) код превращается в «Big Ball of Mud» — высокая связность, сложный рефакторинг, невозможность выделить компонент без переписывания.

**Причина отклонения:** 8 бизнес-доменов разной природы (контент, платежи, чаты, заказы) — классический монолит не обеспечит разделения ответственности и усложнит поддержку уже к Этапу 3–4.

### Вариант B — Микросервисы

Каждый домен — отдельный сервис со своей БД, API, деплоем.

**Плюсы:** полная независимость сервисов, независимое масштабирование и деплой, изоляция отказов.
**Минусы:** колоссальная операционная сложность (8+ сервисов, межсервисная коммуникация, распределённые транзакции, мониторинг, CI/CD на каждый сервис). Требует инфраструктуры (Kubernetes, Service Mesh, API Gateway), которая сама по себе — отдельный проект.

**Причина отклонения:** непосильная операционная нагрузка для одного разработчика — время уходило бы на инфраструктуру, а не на бизнес-логику.

### Вариант C — Модульный монолит с Event-Driven элементами ⭐

Единое приложение, код разделён на автономные модули (по одному на бизнес-домен). Каждый модуль устроен по Clean Architecture (Domain → Application → Infrastructure). Модули взаимодействуют через интерфейсы (синхронно) и доменные события (асинхронно). Единая БД с разделением по схемам.

**Плюсы:** простота деплоя и отладки (одно приложение), чёткие границы модулей (будущие швы для микросервисов), Event-Driven для длительных процессов, единая БД упрощает транзакции и миграции.
**Минусы:** границы модулей держатся на дисциплине — физического разделения нет. Единая БД может стать узким местом при очень высокой нагрузке.

## 3. Decision (Принятое решение)

Архитектурный стиль backend — **модульный монолит (Modular Monolith)** с элементами **Event-Driven Architecture**.

- **8 бизнес-модулей:** Auth, Users, Dishes, Media, Subscriptions, Notifications, Social, Orders. Каждый — отдельный набор проектов (Domain, Application, Infrastructure), физически разделённых на уровне .NET solution.
- **Shared Kernel (Common):** общие примитивы (`Entity`, `AggregateRoot`, `ValueObject`, `Result`), CQRS-абстракции (`ICommand`, `IQuery`), инфраструктурные сервисы (middleware, DI-расширения). Бизнес-логики не содержит.
- **Единая точка входа (WebAPI):** один ASP.NET Core-проект, компонующий модули через DI — каждый модуль регистрируется вызовом `AddXxxModule()`.
- **Межмодульное взаимодействие:** синхронно — через контрактные интерфейсы (`IAuthUserService`, `IMediaService`, `ISubscriptionAccessService`); асинхронно — через доменные события (MediatR in-process, с переходом на RabbitMQ при выделении модулей).
- **Единая БД PostgreSQL** с разделением по схемам — по одной на модуль (ADR-0004).

---

## 4. Rationale (Обоснование)

1. **Размер команды — главный фактор.** Один junior-разработчик не способен эффективно поддерживать инфраструктуру микросервисов. Модульный монолит даёт единый процесс, единую БД, единый деплой — при сохранении логического разделения.
2. **Ясные границы доменов.** 8 доменов с различной ответственностью кодифицированы на уровне проектов и пространств имён — логика не слипается.
3. **Подготовка к эволюции.** Чёткие границы + Event-Driven взаимодействие = готовые «швы» для выделения в микросервисы. Первые кандидаты: Notifications (слабо связан, асинхронный), Media (другой тип нагрузки, CDN), Auth (критическая безопасность).
4. **Event-Driven для отказоустойчивости.** Процессы с внешними зависимостями (заказ → оплата → доставка) — через события; сбой внешнего провайдера не блокирует процесс.
5. **Простота отладки.** Весь стек-трейс в одном процессе; Correlation ID + структурированные логи (Serilog → Seq) достаточны для трассировки — распределённый трейсинг не нужен.

## 5. Consequences (Последствия)

### Positive (Положительные)

- Один процесс — простой деплой (`docker compose up`), простая отладка (F5 в Visual Studio), единый pipeline CI/CD.
- Транзакции внутри одной БД — нет распределённой консистентности (Saga не нужна на Этапах 0–4).
- Структура модулей соответствует Bounded Context из DDD.
- Код демонстрирует архитектурную зрелость в рамках дипломного проекта.

### Negative / Trade-offs (Отрицательные / компромиссы)

- Границы модулей держатся на дисциплине разработчика — физического барьера нет.
- Масштабирование только всего монолита целиком.
- Единая БД — потенциальное узкое место. Митигация: read-реплики, кеширование (Redis, Этап 8+).

### Areas of Caution (На что обратить внимание)

- При ревью проверять, что модули не обращаются к внутренностям друг друга — только интерфейсы-контракты и события.
- Не создавать FK между схемами разных модулей — связь только через Id (детали — ADR-0004; пример последствий — ADR-0007).
- Навигационные свойства EF Core не пересекают границы модулей.

## 6. Future Scope (Будущие направления)

- **Этап 8+:** выделение первых кандидатов (Notifications, Media, Auth); замена in-process событий на RabbitMQ (ADR-0005); замена контрактных интерфейсов на HTTP/gRPC-клиенты.
- **При росте команды:** физическое разделение репозиториев по модулям, отдельные CI/CD-пайплайны.
- **При росте нагрузки:** Database per Service для самых нагруженных модулей, API Gateway (YARP/Ocelot).

## 7. Implementation Reference (Связь с кодовой базой)

- `GastronomePlatform.sln` — solution с папками `src/Common/`, `src/Modules/`, `tests/`.
- `src/Common/GastronomePlatform.Common.{Domain,Application,Infrastructure}` — Shared Kernel.
- `src/Modules/{Auth,Users,Dishes,Media,Subscriptions}/` — реализованные модули (каждый из 3 проектов); Notifications, Social, Orders — этапы 5+.
- `src/GastronomePlatform.WebAPI/Program.cs` — композиция: `AddAuthModule(...)`, `AddUsersModule(...)`, `AddDishesModule(...)`, `AddMediaModule(...)`, `AddSubscriptionsModule(...)`.
- `docker-compose.yml` — инфраструктура (PostgreSQL, RabbitMQ, Seq).
